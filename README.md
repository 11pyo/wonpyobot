# 원표봇 (Wonpyobot) — 담당자가 자리를 비운 사이, 문의를 받아 1차 대응하는 에이전트

> **한 사람이 창구인 조직에서, 그 사람이 없을 때 창구를 닫지 않는 방법.**
> 사내망 접수 창구 + 이벤트 기반 감시자 + **쓰기 게이트**로 이루어진 무인 1차 대응 체계.
> 이 저장소는 **익명화된 참조 구현**과 설계 노트다. 실제 회사 데이터는 들어 있지 않다.

[English](README.en.md) · **한국어**

## 무엇을 푸는가

운영 담당이 한 명인 조직에는 구조적 공백이 있다.

- 담당자가 휴가·출장·교육으로 자리를 비우면 **문의 대응이 멈춘다.**
- 현업은 언제 답이 올지 모르고, 급하면 아무나 붙잡는다.
- 담당자는 복귀 후 **밀린 것을 한꺼번에** 받는다.

원표봇은 그 공백을 **완전히 메우려 하지 않는다.** 대신 이렇게 나눈다.

| 구간 | 누가 |
|---|---|
| 접수 확인 · 아카이브/선례로 확정되는 문의 | **원표봇** (몇 분 내) |
| 판단이 갈리는 건 | **대기** — 담당자 복귀 후 |
| 업무가 멈출 만큼 급한 건 | **지정된 사람에게 에스컬레이션** |

**"AI가 다 한다"가 아니라 "AI가 어디까지 하는지 문서로 못 박는다"** 가 이 설계의 축이다.

## 구조

```
현업 브라우저 ──▶ 접수 서버 ──▶ 로그 파일(append-only)
                                    │
                              (파일 변화 감지)
                                    ▼
                                 감시자 ──▶ LLM 호출 ──▶ 판정 JSON
                                    │                        │
                                    └──▶ 쓰기 게이트 ◀───────┘
                                              │
                                    (표기 부착·검증·기록)
                                              ▼
                                         로그 파일
```

### 설계의 핵심 세 가지

**1. 에이전트에게 쓰기 권한을 주지 않는다**

LLM 에게 "파일에 기록하라"고 시키면, 명령 형태가 조금만 달라져도 권한 검사에 걸려 **조사만 하고 조용히 끝난다.** 실제로 그렇게 실패했다 — 조사는 완벽했는데 답변이 기록되지 않았고, 아무도 몰랐다.

→ 에이전트는 **판정 JSON 만 돌려준다.** 파일에 닿는 것은 게이트 하나뿐이다.

**2. 게이트가 사람 대신 규칙을 지킨다**

에이전트가 빠뜨릴 수 없도록 게이트가 강제한다.

- AI 답변임을 밝히는 **표기를 자동 부착** (지울 수 없다)
- 내부 메모는 **답변란에 들어가지 못한다** — 애초에 다른 경로로 간다
- AI 는 문의를 **완료로 닫지 않는다** → 전부 「대기」. 사람이 보고 닫는다
- 기록 후 **재조회로 확인** — 성공 메시지는 반영의 증거가 아니다
- **사용자가 실제로 볼 문장까지 렌더해서 검증**

**3. 폴링이 아니라 상태 기반(level-triggered)**

"어디까지 처리했나"를 기억하지 않는다. 매번 **파일 전체에서 처음부터 계산**한다.

- 감시자가 3시간 죽어 있었어도, 켜지는 순간 밀린 것을 전부 잡는다
- 오프셋을 기억하는 방식은 쓰기 도중에 읽으면 그 건을 **영영** 놓친다
- 빈 대기 구간에는 LLM 을 부르지 않는다 → **비용 0**

## 값비싸게 배운 것들

이 저장소의 진짜 내용은 코드가 아니라 이 목록이다. 전부 **실제로 터진 것**이다.

| 무엇이 터졌나 | 왜 위험한가 | 어떻게 고쳤나 |
|---|---|---|
| 에이전트에게 준 쓰기 권한이 명령 형태 불일치로 거부됨 | 조사만 하고 **침묵**. 아무 신호도 없다 | 쓰기 권한을 회수하고 게이트로 일원화 |
| 안전장치(“출력이 30% 이상 줄면 표준문구로 대체”)가 **대화 전체를 갈아엎음** | 안전장치가 데이터를 파괴 | **이번 턴에 새로 쓰는 글만** 검증 |
| 접수 확인 안내 위에 답변이 달리자 **필수 표기가 떨어져 나감** | 사용자가 확정 답변으로 오해 | 실제 답변 위에만 이어붙이도록 분리 |
| 데몬이 상태 파일을 통째로 덮어써 **「종료」가 되돌려짐** | 껐는데 계속 돈다 | 프로세스마다 **소유 필드**를 나눔 |
| 서버가 조용히 죽었는데 감시자는 정상 | 접수 자체가 안 되는데 지표는 초록불 | 감시자가 **창구 생존을 확인하고 되살림** |
| 같은 포트에 **두 프로세스가 동시에 바인딩**(Windows) | 옛 프로세스가 옛 코드를 계속 서빙 | `allow_reuse_address = False` |
| 서빙되는 JS 의 문법 오류로 **화면 전체가 죽음** | 버튼도 탭도 반응 없음 | 배포마다 **서빙본 문법 검사** |
| 채점용 사본에 **정답지가 같이 들어 있었다** | 시험 대상이 정답을 읽으면 점수가 아무것도 말해 주지 않는다 | 사본에서 정답지를 빼고, **뺐는지를 시험으로 확인** |
| 실행이 실패한 사례를 **0점으로 평균에 섞었다** | 도구의 고장이 「AI가 틀렸다」로 기록된다 | 실행 실패는 **0점이 아니라 제외**하고 건수를 따로 보고 |
| 시험 삼아 띄운 서버 사본이 **사용자 화면에 브라우저 탭을 계속 열었다** | 시험을 돌릴 때마다 「연결 거부」 탭이 쌓인다 | 정본 서버의 부수효과 끄기 옵션을 기동 경로 그대로 쓰고, **서버 로그로 꺼졌는지 확인** |

공통점이 있다. **거의 전부 "조용히 실패"였다.** 로그도 초록불, 지표도 정상, 그런데 사용자 쪽에서는 아무 일도 일어나지 않는다. 무인 시스템에서 가장 비싼 실패는 멈추는 게 아니라 **멈춘 줄 모르는 것**이다.

그래서 이 설계는 **하트비트·창구 생존 확인·복귀 보고서의 "끊김 시간"** 을 전부 남긴다. 복귀했을 때 *"문의가 없었다"* 와 *"멈춰 있었다"* 를 구분할 수 있어야 한다.

## 얼마나 믿어도 되는가 — 측정

무인 대응의 범위를 넓히려면 「이번 주에 잘 됐다」가 아니라 **숫자**가 필요하다. 이 설계는 답 하나하나를 장부에 남기고, 사람이 검토한 결과를 기준으로 자동화 단계를 올린다. 그 과정에서 배운 것:

**1. 「20건 연속 무오류」는 안전의 증명이 아니라 속도 관문이다.**

전부 맞았어도 표본이 작으면 「정확도가 얼마 이상」이라고 말할 수 있는 폭이 좁다. 95% 신뢰구간(Wilson) 하한은 이렇다.

| 연속 무오류 | 1건 | 20건 | 50건 | 100건 |
|---|---|---|---|---|
| 정확도 하한(95%) | 21% | 84% | 93% | 96% |

정확도가 최소 90% 라고 말하려면 **35건**, 95% 라면 **73건**이 필요하다(`n / (n + 3.84)`). 그래서 단계 기준 건수 옆에 **하한을 같이 표시**하고, 기준을 넘겼다는 이유만으로 권한을 열지 않는다. `reference/trust_bound.py` 가 이 숫자를 다시 만든다.

**2. 단계마다 재는 대상이 다르다.**

「단순 문의의 답」과 「개발 의뢰의 분류」를 한 통에 섞어 세면 어느 쪽 정확도도 말할 수 없다. 단계마다 **문의 유형 · 판정 종류**로 모집단을 정하고 그 안에서만 센다.

**3. 표본이 모자라면, 실시간을 기다리지 말고 과거 사례를 다시 돌려 잰다.**

과거 문의를 **같은 프롬프트 · 도구 · 격리 조건**으로 다시 돌려 점수를 낸다(재생 평가).

- 시험 대상이 보는 것은 **정답지가 빠진 지식 사본**과 **가짜 접수 서버**뿐이다 — 운영 기록에 닿지 않는다
- 채점은 **도구를 못 쓰는 별도 LLM** 이 답의 출처를 모르는 채로 **항목별로만** 매긴다. 상한(「이러면 최대 N점」) · 감점 · 합계는 **코드가** 계산한다 — LLM 에게 합계를 맡기지 않는다
- 실행이 실패한 건은 **0점이 아니라 제외**하고 건수를 따로 보고한다. 「답을 하나도 안 냈다」는 0점으로 센다
- 사례 세트가 다르면 **점수를 비교하지 않는다**(세트 지문으로 확인). 두 버전의 차이는 짝지은 부트스트랩 신뢰구간으로 본다
- 채점 LLM 도 검증 대상이다 — 이전 채점과의 일치를 **이전 채점자끼리의 흔들림**(같은 답을 두 번 채점했을 때의 차이)에 견준다

이 도구는 회사 자료와 얽혀 있어 이 저장소에는 넣지 않았다. **방법만** 적는다. 새로 짜는 쪽이 사례 세트와 채점 기준을 자기 조직의 것으로 채워야 한다.

## 참조 구현

`reference/` 에 **돌려볼 수 있는 최소본**이 있다. 회사 코드가 아니라 같은 구조를 새로 쓴 것이고, 데이터는 전부 가상이다.

```bash
cd reference
python demo.py            # http://127.0.0.1:8710 열림
```

`demo.py` 하나에 접수 서버 · 감시자 · 쓰기 게이트가 다 들어 있다. LLM 호출부는 **교체 가능한 함수** 로 빼 두었으니, 쓰시는 모델로 바꿔 끼우면 된다.

`rules.sample.md` 는 위임 범위 문서의 견본이다. **이 문서가 시스템의 정본이다** — 코드가 아니라.

`trust_bound.py` 는 위 측정 절의 표를 다시 만드는 최소 계산기다(표준 라이브러리만).

## 한계 — 쓰기 전에 알아야 할 것

- **이 PC 가 서버다.** 꺼지면 접수 자체가 안 된다. 기존 창구(메신저 등)와 **병행**해야 한다.
- **본인 확인은 이름 일치 수준**이다. 로그인이 없다. 사내망 전제이며, 답변에 민감정보를 적지 않는 것이 방어선이다.
- **에이전트는 위임 범위 밖을 답하지 않는다.** 그 건들은 대기로 쌓인다. 긴 부재라면 **사람 백업이 반드시 필요하다.** 도구로 메울 수 없다.
- **측정 표본은 작다.** 무오류 20건은 「정확도 84% 이상」이라는 뜻일 뿐이다. 단계 기준을 넘겼다는 것과 안전하다는 것은 다른 말이다.
